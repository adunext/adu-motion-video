# 素材色彩与可追溯预览

这套流程用于新制作。已经交付的影片不因增加检查而自动重渲染，也不能通过补写标签或 manifest 被追认为已验证。

## 导入时确定颜色

`import_talk.py` 探测源范围、矩阵、传递函数、色域、实际像素格式和位深、Dolby Vision 元数据，记录源文件 SHA 与大小。HLG/PQ 按显式色彩参数转 SDR，再进入浏览器的 sRGB 图像合成；普通 SDR 不套 HDR 色调映射。导出进行 sRGB → BT.709 转换，并核对真实输出流的 limited range / BT.709 标签。仅改标签不能代替转换。

低位深 HDR、未知 HDR 位深、缺 SDR 元数据或仅处理 Dolby Vision 基础层时，会产生 `reviewSignals`。这些情况需要实际对照：同一时间、同一人物区域，比较可信的原生播放器参考、导入帧和最终成片。先排除旧文件、旧标签页、重复转换，再判断色调映射；不能凭肤色偏暖就自动加冷色或修改白平衡。

把实际检查记为 JSON，通过 `import_talk.py --color-review 文件.json` 或本期 spec 的 `colorReviewFile` 传入。记录格式：

```json
{
  "sourceSha256": "实际源文件的64位SHA256",
  "decision": "accepted",
  "reviewer": "实际执行检查的人或代理",
  "reviewedAt": "2026-10-03T15:00:00+08:00",
  "reference": "实际对照图或原生播放参考的位置",
  "notes": "实际观察与限制，不能只写标签正确",
  "acceptedSignals": ["与本次探测完全对应的风险代码"]
}
```

该记录是已做视觉对照的证据，并非新增用户审批环节；执行者可记录自己的检查，不冒用用户身份。没有做对照时，不填 accepted。

完整组的通用 `video` 槽也使用同一 HDR/SDR 转换，独立写入 `media_color.json`，绑定每个分镜槽的源 SHA、转换参数与实际 JPEG 帧 SHA。每段视频需要对照记录时，在该槽提供 `{path, offset, colorReviewFile}`；记录必须匹配那段视频，口播的顶层记录不能代替它。新导出及发布会核对这些帧和记录，缺失或改变后不能继续宣称验证通过。正常 10 位 HDR 的技术转换不会自动要求风险记录，但仍需看最终画面；转换成功不代表肤色已经过人眼确认。

素材适配检查按显示旋转和像素宽高比计算画面比例。同路径文件被覆盖后重新探测，不能沿用旧尺寸或旧时长。已有图片和旧序列仍属于预处理素材，不能仅凭其扩展名证明上游色彩正确；需要追溯它们的原视频和实际处理记录。

## 发布当前版本

```bash
bash "$PL" render /路径/新工程 /路径/新片_v1.mp4
bash "$PL" preview /路径/新工程 /路径/新片_v1.mp4 /已存在父目录/新预览目录
# 下一版通过同样检查后更新这个生成的预览目录
bash "$PL" preview /路径/新工程 /路径/新片_v2.mp4 /已存在父目录/新预览目录 --update
```

发布前直接核验影片 SHA、完整解码、实际色彩标签、逐帧时钟、片段覆盖和导入证据。输出使用 `video-完整SHA.mp4`，页面显示当前播放的版本，下载指向同一份文件。旧页面恢复焦点或定时检查发现新版后显示更新提示，由使用者载入；不会播放中途偷换影片。检查失败时显示“版本未确认”，不能继续宣称是最新版。

`verified` 只代表这项技术核验通过。它不等于肤色、字幕、每个外部素材或连续声画全部获认可；仍须观看和试听最终编码文件。原始私有素材及人工记录中的参考路径不会放进公开 `delivery.json`。
